# モデルの画像とメモリ

操作窓の「モデルと操作」を開くと、「モデルの画像」で「元の画質」と「メモリを抑える」を選べる。初期設定と、以前の設定ファイルを使った起動では「元の画質」を維持する。選択は次の起動にも残る。

「メモリを抑える」では、表示に使う大きな画像だけを縮小する。細かい模様や髪の質感が変わる場合があり、モデルによって効果も異なる。気になる場合は「元の画質」へ戻せる。選択したVRMファイルは読み取るだけで、縮小版のファイルを作ったり元ファイルを書き換えたりしない。

切り替えるとモデルを読み直し、読み上げをオフにして、移動中の操作・窓の選択・窓への追従を解除する。声を使い続ける場合は、会話設定の「声で話す」を再びオンにする。位置、姿勢、大きさ、向きは維持する。隠している場合は、切り替えだけでは表示しない。同じ選択を繰り返しても読み直さない。通常の起動・隠す・戻す・終了の操作は[README](../README.md)に記載している。

## 実装と限界

compact設定では、長辺が1024を超えるImageBitmap（展開済み画像）を、縦横比を保って一度だけ縮小する。小さい画像には処理を加えない。1024は、標準300×440・最大360×528の常駐表示での比較から選んだ試作値で、すべてのモデルに最適という意味ではない。

Threeの通常の画像デコード後、parserごとのアダプターから`createImageBitmap`を呼ぶ。元画像に適用済みの向きを二重に反転せず、アルファと色変換の指定を保つ。高品質の補間を指定するが、縮小は元の画素を保つ処理ではない。[HTML StandardのImageBitmap仕様](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html#createimagebitmap)

縮小が終わるまで一時的な所有者が元画像を保持し、終わると元画像を解放する。別のモデルが同じ画像を使っている場合は、その所有者が使い終わるまで閉じない。表示中の縮小画像はGPU描画の復帰に必要なので保持し、モデル破棄時に閉じる。読み直し・取消後に古い縮小処理が終わっても、現在のモデルの画像を閉じたり、元の画質に戻した選択を上書きしたりしない。

縮小に失敗した画像は元の画像を使う。モデルの画像を欠落させず表示を優先するため、一部の画像が縮小されない場合がある。検証用の診断には`resizedImages`と`imageResizeFallbacks`を記録する。もともと大きな画像がないモデルでは、メモリの減少は期待できない。

元画像を一度展開してから縮小するため、**読込中の最大メモリ量を下げる方式ではない**。一時的に元画像と縮小画像が共存し、縮小の処理時間も加わる。ライブラリ・外部サービスの追加、画面全体の監視、追加のAPI料金はない。

## 検証方法

`npm run check`の後、画像を使うローカルVRMを選択済みの環境で`npm run test:texture-quality`を実行する。少なくとも1枚の画像が長辺1024を超えるモデルが必要。通常設定とは別のテスト設定で、切り替え・取消・非表示・復帰・保存と再起動を検査する。実モデルの画像を読み、結果とアプリ自身のPNGはGit対象外の`work/texture-quality-*/`へ保存する。外部AIやVOICEVOXへは接続しない。

2026-09-10の製品設定の受け入れ検査は13項目成功。実UIの切り替え・保存と再起動、無効な設定と送信元の拒否、縮小失敗時の元画像への復帰、非表示中や描画停止中の変更、古い縮小の遅延完了、モデル未選択での設定を含む。21個の記録対象プロセスが終了し、通常設定のバイト一致も確認した。記録は`work/texture-quality-cZtMr4/result.json`。

製品の実際の設定を使った比較では、同じモデル・静止表示・会話窓なしで、元の画質→メモリを抑える→メモリを抑える→元の画質の順に4つの新しいアプリを起動した。各起動で1回読み直し、8秒待ってから2秒間隔で6回測った。画像を置き換えない観測用フックだけを使い、通常の製品の縮小処理を通している。

| 起動順 | アプリとWindows補助のWorking Set平均 | Private Bytes平均 |
| --- | ---: | ---: |
| 元の画質 1 | 706.11 MiB | 786.68 MiB |
| メモリを抑える 1 | 620.71 MiB | 707.87 MiB |
| メモリを抑える 2 | 620.02 MiB | 704.60 MiB |
| 元の画質 2 | 648.76 MiB | 723.56 MiB |

Working SetはRAM上のページ量で、プロセスの合計は共有ページを重複計上し得る。設定ごとの平均は677.44→620.36 MiB（約57.07 MiB減）だったが、元の画質側だけでも起動間で約57.35 MiB違った。削減率を保証できる測定ではない。CPUは約0.027〜0.046%で、改善の根拠にはしない。GPUメモリ自体は直接測っていない。

保持した26画像のRGBA換算は88.25→52.25 MiBで、2048角の3枚を縮小し、元画像は各1回だけ閉じた。縮小失敗は0件。最初の縮小設定の描画復旧では画像を追加作成せず、復旧前後の画素が一致した。標準・大サイズの立ち姿と座り姿を比較し、顔・髪・服に目立つ欠落や反転は見られなかったが、縮小によって画素は変化する。細部が同じ・無劣化とは主張しない。全4起動の非表示・再表示、24個の記録対象プロセスの終了、通常設定のバイト一致も確認した。記録は`work/texture-product-compare-PK5NQJ/result.json`。詳しい範囲は[検証記録](evaluation.md)に残す。

導入前の試験はrenderer内の一時的な縮小フックを使ったため、上の製品設定の測定とは分ける。記録は`work/texture-compare-U8Di9c/`。Working Set合計は平均675.72→625.36 MiB、元の画像側の起動間の差は約48 MiBだった。GPUプロセスのWorking Setは約11 MiB増えており、この試験からもGPUメモリを削減したとは言えない。

別モデル、長時間使用、電池持ち、実スリープやGPUドライバー障害での復帰は未検証。基本の常駐コストは[メモリの内訳](resident-memory.md)に残しており、今回の選択肢だけで省メモリなアプリになったとは扱わない。
