# 普段そばに置きたいしずくへ

2026-09-10、利用者は就活向けの見せ方より、プロダクト自体を良いものとして完成させることを優先した。しずくの基準は、静かにいて、呼べば応え、作業を邪魔せず、また明日も起動したくなること。

## 最初の完成範囲

Windows・主画面1枚・手動起動から、次の一連の使い方を仕上げる。複数画面、万能なPC操作、常時マイク・画面監視は含めない。

| 場面 | 仕上がりの基準 | 現在の不足 |
| --- | --- | --- |
| 起動して置く | 必要な準備が分かり、選んだ場所・姿・大きさで静かに現れる | 新しい環境の導入手順、初回のモデル選択、音声起動の手間を実使用で見直す |
| 作業のそばにいる | 背後のクリックや入力を妨げず、表示・音・負荷が気にならない | 直接ドラッグの焦点問題、メモリ、様々な窓との組み合わせ、長時間使用 |
| 呼んで話す | 呼びかけへの反応、短い返答、声と口の動きの間が自然で、中止できる | 実AIから実音声までの通し確認、聞きやすさ・返答の長さ・待ち時間の評価 |
| 作業へ戻る | 会話を閉じると静かな常駐へ戻り、履歴や古い音声が勝手に復活しない | 実際の作業の流れで繰り返し使った確認 |
| 困ったら止める | 非表示・再表示・画面端への復帰・終了が確実で、失敗時の戻り方が分かる | 実スリープ・ロック、別PC、利用中の障害と復帰の確認 |

## 現在までの改善

2026-09-11、送信ボタンのクリック後に入力欄へ戻るようにし、待つ間に利用者が別の設定や窓を操作した場合は、その操作を優先するよう整えた。設定を開いているときのEscは設定だけを閉じ、会話を誤って破棄しない。会話窓の応答不能通知では本体側から窓を閉じ、会話・返答待ち・音声を破棄する。再生中と合成待ちに模擬通知を送り、口を閉じ、古い結果が再生されず、新しい会話が履歴なし・定型返答・音声オフになることを確認した。実際のハングを起こした検査ではない。

132単体テスト・Build・audit 0件、実Electronの会話13項目・AI11項目・音声20項目が成功した。ただしPlaywright/CDP（自動操作用の接続）付きの高速検査で、操作窓の終了完了前に会話窓の破棄が重なる条件では、検査接続が2回切れ、うち1回で本体のネイティブ異常終了コードを記録した。操作窓の`closed`通知を待つ検査で会話13項目が成功したものの、同じ条件を旧版f970bccと今回の版で各1回比較すると両方で再現した。CDPのfocus模擬だけを有効に戻した追加1起動では、終了の重複を維持したまま正常終了した。旧版にも存在する症状で、焦点の検査設定による違いは分かったが、ネイティブ側の根因と実操作への影響は未確定。急な閉じ方全般が安全、または日常利用が完成したとは判定しない。詳細は[検証記録](evaluation.md)に残す。

[常駐と会話20回の連続検査](daily-use.md)を追加し、約14分の4区間でCPU平均約0.048〜0.057%、Working Set平均約470〜600 MiBを記録した。終了時の検査判定の誤りにより本実行の総合failedは保持し、製品Buildを変えず検査を強化した約166秒の短縮実行で、会話20回すべての実窓・描画処理の破棄、正常終了、残存PID0を確認した。数値は静止・同一モデルでの順次切替による結果で、画質設定の一定の削減率や終日の安定性は示さない。利用者が実際に呼んで話し、作業へ戻るときの邪魔や自然さを引き続き評価する。

2026-09-10、[モデル画像の設定](texture-quality.md)に任意の「メモリを抑える」（compact）を追加した。初期値は「元の画質」（original）を維持し、モデルファイルは書き換えない。画質への影響と、読み直しによる窓の追従解除を選択時に説明する。

実装した設定を元→省→省→元の順で短時間比較し、静止表示・会話なしの本体と補助のWorking Set平均は677.44→620.36 MiBだった。元側の2回にも約57 MiBの差があるため、一定量の削減とは扱わない。保持画像のRGBA換算（幅×高さ×4バイト）は88.25→52.25 MiBに減った。今回のモデル・表示サイズでは目立った見た目の破綻を認めず、縮小画像での描画復旧を確認した。132単体テスト・Build・audit 0件・実Electronの設定受入13項目が成功した。

これは一つのモデルでの短時間確認。長時間の負荷、別モデルの効果と画質、実スリープ・ロック、会話と音声の自然さは未解決で、上の完成基準を満たしたとはしない。[検証記録](evaluation.md)では、以前の測定・実入力・内部操作の検査と区別する。

## 進める順番

1. 任意の省メモリ表示の比較を踏まえ、[常駐と会話の連続検査](daily-use.md)、長時間と別モデルで負荷・画質・復帰を確かめる。開閉が重なる高速検査の終了異常も切り分ける。画質に影響する変更は説明し、違いを実画面で確認する。モデルファイル自体は書き換えない。
2. 利用者が自分の作業で使い、「邪魔だった」「待ちすぎた」「操作に迷った」ところを具体的に直す。会話・音声の有効化と外部送信の境界は維持する。
3. 呼ぶ→短い会話→閉じる、という流れの待ち時間・声・視線・動きを整える。新機能より、この流れの不自然さを優先する。
4. 新しい環境での準備、数時間の利用、休止と復帰、終了を確認し、対象条件を明示した最初の利用版にする。

専用の外見と声の最終的な印象は、しずくの体験に関わる判断として利用者と決める。現在の検証モデルを、制作済みのしずく専用モデルとは扱わない。市販DLCや未確認の素材は使わず、素材・音声・ソースの権利は別々に確認する。

## 完了の判定

テスト件数や機能数だけで完成としない。既存の安全性・停止・復帰の検査に加え、利用者が普段の作業で試した結果、同じ条件で比較した負荷、見た目と聞こえ方を判断材料にする。未検証の環境や制限は残す。ソースがPublicであることと、日常利用を勧められる完成度は別の状態として記録する。
