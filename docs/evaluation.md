## モデル画像の解放（f71bc0d）

VRMを片付ける際、GPU上のテクスチャは解放していたが、CPU側の画像に対する`ImageBitmap.close()`を呼んでいなかった。ThreeのGLTFLoaderはこの画像を明示的に解放するよう注意している。[Threeの公式説明](https://threejs.org/docs/pages/GLTFLoader.html)

実モデルの`createImageBitmap`と`close`を検査中だけ計測した。修正前は再読込3回で生成26→52→78個、明示解放は0個のまま。修正後は生成数が同じでも解放0→26→52個となり、使用中の画像は26個に保たれた。これは生成と解放の呼出しの観測であり、その個数をそのまま実メモリ使用量に換算しない。

読み込みを重ね、古い画像の到着を遅らせた検査でも、新しいモデルの26個を維持し、合計130個のうち古い104個を解放。表示をクリアすると130個すべてが一度ずつ解放された。再読込後のキャンバスで服・髪・肌の描画が残ることを目視した。検査後のアプリプロセス消滅と通常設定の一致も確認。生データは`work/resources-DQrXFF/result.json`、修正前は`work/bitmap-probe-Syp8KX/result.json`。

読込単位で所有画像を管理し、そのモデル専用のローダーで追跡する。全体の画像APIは書き換えない。同一画像の重複・共有所有者・取消後の遅延到着・失敗時の管理を6件の単体テストで検査した。Three r185の内部ローダーに依存する小さな接続部分があるため、依存関係を更新するときは本物の画像を使う`npm run test:resources`も再実行する。

型検査・単体テスト42件・Build、既存のElectron検査23項目、実画像の資源検査が成功。依存関係の追加なし、`npm audit`の既知の脆弱性0件。反復読込試験では、古い読み込みの追加画像を新しい世代として数える検査側の問題を修正し、新モデルの画像IDを解放前に確定する方法で再検査した。

常駐時の描画上限30fpsは変更していない。15fpsへの変更案は、髪・服の物理的な減衰も変わる可能性があるため見送った。今回の修正が扱うのは、主にモデル再読込時の画像の後始末である。

## 修正後の短時間常駐と反復操作（f71bc0d）

同じWindows PC、16論理CPU、主画面の作業領域1920×1032・倍率100%、AvatarSample_A、標準300×440で計測。20秒の準備後、表示5分・非表示1分を別々に測り、続いて呼ぶ・隠す・戻す・3サイズへの変更を15回繰り返した。全操作が完了し、通常設定は一致、終了後の記録対象PIDは0。全体約7分17秒であり、数時間の安定性やスリープ復帰を確認したものではない。

CPUは4つのアプリプロセスの累積CPU秒差を経過秒・16論理CPUで割ったPC全体比。メモリはWorking Setの合計で、共有ページを重複して数える場合がある。Private Bytesは専用に割り当てた量で、常にRAM上にある量ではない。Playwrightが2秒ごとにmainと描画側を読む検査を含み、他アプリを停止した専用環境ではない。

| 測定 | 表示中 | 非表示中 |
| --- | --- | --- |
| CPU平均（検査処理を含むPC全体比） | 1.047% | 0.489% |
| Working Set平均／最大 | 482.30／528.84MiB | 480.07／480.53MiB |
| Private Bytes平均／最大 | 474.47／523.04MiB | 471.20／471.68MiB |
| CPU・メモリの測定時間／時点数 | 300秒／151 | 60秒／31 |
| 描画 | 平均25.85fps | 8278フレームのまま、追加描画0 |
| GPU平均／最大（アプリに帰属する最も使用率の高い物理エンジン） | 3.995／8.477% | 0／0% |
| GPU有効サンプル数／最初から最後までの時間 | 53／106.01秒 | 28／54.94秒 |

**非表示CPUは測定経路による差が大きい。** 上記60秒ではGPUプロセスがCPUを2.476秒、描画プロセスが2.115秒使った一方、実際のGPU Engine使用率とアプリ描画数は0だった。補足として、同じ生成コードをPlaywrightなし・描画側への問い合わせなし・GPUカウンター採取なしで起動し、表示10秒と非表示直後2秒を除外して約30.07秒測ると、CPUは0.042%だった。記録は`work/hidden-native-yN0rmY/result.json`。複数の計測条件が違うため原因は断定せず、0.489%を通常起動の定常負荷と決めつけない。逆に補足値だけで長時間の軽さを保証しない。

表示中のメモリは最初528.46MiBから最後479.60MiBで、この5分間に増え続ける様子はなかった。モデル再読込時の画像解放は改善したが、以前の約494MiBとの差を今回の修正効果とは断定しない。通常表示でも約482MiBを使っており、さらに負荷を検討する余地がある。

GPUの最初の採取は実アプリPIDの準備前に始めたため中断し、表示区間の途中から採り直した。欠測を0として補っていない。再採取85サンプルはすべて有効で、表示変更をまたぐカウンターを避けるため、各区間の開始後2秒と区間外を集計から除外した。起動前のPID確定処理を検査スクリプトへ追加し、`pidsReady`で準備済みか確認できるようにした。この補修は測定対象アプリの描画コードを変更しない。

生データは`work/soak-bA9zjD/run.json`、`gpu.json`、`gpu-summary.json`。同じ実行内の結果だけを組み合わせる。CPU・メモリ・反復操作は`npm run soak`で再実行できる。GPUも測る場合はPowerShell 7の別窓で、`soak`開始後に次を実行する。

```powershell
$soakRun = Get-Content work/soak-active.json -Raw | ConvertFrom-Json
if (-not $soakRun.pidsReady -or $soakRun.status -ne 'running') { throw '計測を開始し、PIDの準備完了を待ってください。' }
./scripts/measure-gpu.ps1 -Samples 195 -PidsFile (Join-Path $soakRun.directory 'pids.json') -Output (Join-Path $soakRun.directory 'gpu.json')
```

`soak`とGPU採取の両方が終了した後、`node scripts/summarize-soak-gpu.mjs`で集計する。計測途中や失敗したrunは集計を拒否する。別の実行を始めた場合は対象フォルダを引数で指定し、古いGPUファイルを混ぜない。

形状指定にはWindows対応の実験的API `setShape` を使用。空配列は窓全体へ戻るため、必ずクリック通過を先に有効にする。矩形の数・座標・範囲・送信元を検査し、不正な輪郭は移動を取消。古い移動セッションの入力が次の移動を変更しないことも検査する。[Electronの形状仕様](https://www.electronjs.org/docs/latest/api/base-window#winsetshaperects-windows-linux-experimental)

なお、CSSの標準ドラッグ領域は今回の非フォーカス窓で動かなかったため採用していない。押下・移動・解放イベントで自分の窓だけを動かし、開始時のつかんだ位置を保持する。生の実機記録はGit管理外の `work/native-move-check.json`。

- 表示300×440、DPR1、30fps上限、影なし。実測FPSは上限より低く、30fps固定達成を主張しない。
- CPUは同一プロセスの累積CPU秒の差分を、区間の経過秒と16論理CPUで割ったPC全体比。時間で重み付けして平均する。メモリは対象プロセスのWorking Setの合計（共有ページの重複を含み得る）とPrivate Bytesの合計（割り当て済み専用メモリで、常にRAMへ載っている量ではない）。
- 表示・非表示を別の期間として集計し、それぞれ最初の10秒を除外。モデル読込済み、同じ4プロセスのPIDと起動時刻、単調に増える時刻、測定範囲を検証した。古いログ、不正値、区間内の表示状態変更は成功として扱わない。
- GPUはWindows `GPU Engine/Utilization Percentage` を2秒間隔で取得。同一物理エンジンについて対象PIDを合算し、最大値を代表値にする。PC全体のGPU使用率とは異なる。

| Private Bytes合計・平均／最大 | 481.73／520.98MiB | 465.80／468.94MiB |

| 描画 | 区間末尾25.9fps、途中26.4fps | 約221秒、3,738フレームから増加なし |

GPU取得中にWindowsカウンターの無効値が発生したため、無効値を0にせず除外して非表示区間を再測定した。GPUはCPU・メモリより短い部分区間の測定。以前の「CPU0.41%、メモリ582.2MiB」は表示・非表示・操作窓を混ぜた途中の補足値で、上表とは条件が異なるため置き換えた。

17:13ごろの物理Escapeによる中断後、利用者の再開依頼を受けて続行。18:05に前回からのアプリを正常終了し、保存待ちだった時系列データを確定・集計した。起動から約58分生存していたが、その大半は非表示であり、連続表示の長時間耐久試験とはしない。再開後の更新検査も終了済み。

生データはGit管理外の `work/gpu-visible-final.json`、`work/gpu-hidden-final.json`、`work/measurement-periods.json`、`work/metrics.json` に保持。集計結果は `work/performance-summary.json`。`node scripts/summarize-metrics.mjs` で再集計できる。同じ計測PCでの実行を前提に論理CPU数を取得し、別のPCで集計する場合は環境変数 `SHIZUKU_CPU_COUNT` に計測元の論理CPU数を指定する。

Electronの取得ZIPは158,149,320 bytes（約150.8MiB）、展開した実行本体367.4MiB、開発用依存全体471.8MiB、アプリの生成コード0.75MiB。キャッシュ・VRM・実行データは別。インストーラーの配布容量ではない。

## 現行版で残る確認

- **タイトルバーの実ドラッグは未検証。** 再開後、別アプリのウィンドウが重なり、Computer Useの対象一致チェックでドラッグが拒否された。前面化後も対象外の画面が見えたため、その座標への操作を続けていない。矢印ボタンと移動イベントの追従を、実ドラッグ成功へ読み替えない。利用者の手元での確認を依頼済み。
- 直接移動の追加後、操作窓の実画面を見て開始ボタンからの有効化も確認。タイトルバーへのドラッグ入力は再送できたが窓の座標は変わらず、こちらの手操作相当の成功確認には至っていない。記録は `work/control-title-drag-check.json`。
- 実マウスでの通知領域アイコン選択とメニュー全項目の通し操作は未検証。実際のElectronメニューの処理は検査済み。終了用ショートカットは実操作した。
- トレイの実ダブルクリック、ショートカット競合、壊れたモデル全般、スリープ復帰、長時間、バッテリー、高負荷時、別GPU・別VRM、インストーラー配布は未検証。
- 実機に画面が2枚あるため、物理的に1枚だけ接続した環境を検証したとは言わない。複数画面対応も完成していない。
- 通常時はキャラクター全体がクリック透過。直接移動は明示開始で一度だけ使う。端末内の短い呼びかけ反応は実装済みで、AI会話・音声は未接続。
- 新アプリはlocal Gitのみ。新GitHubの公開範囲・アプリ全体のソースライセンスは未決定。
