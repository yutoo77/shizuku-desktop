# 最小常駐試作の検証記録

2026-09-09、3段階のサイズ調整と端末内の「呼ぶ」反応まで更新。新アプリ自身の結果。既存アプリのテスト件数は流用しない。

## 短い呼びかけ反応

`Ctrl + Alt + Shift + C`、トレイの「呼ぶ」、操作窓の「呼ぶ」を追加。隠していれば非フォーカス表示で戻し、約2.1秒の小さな頷き・首の向き・弱い表情変化で応じる。表情はモデルが持つhappy、なければrelaxedを使う。どちらもないモデルは頷きだけで、動きを減らす設定では表情の応答も見えない。会話・音声・録音・API通信は追加していない。

- Windows上のElectron検査で、操作窓からの開始・自然終了、連打しても延長や待ち行列が発生しないこと、トレイのコールバックで非表示から応じることを確認。呼ぶショートカットは登録を確認したが、物理キー入力は未検証。
- 隠すと反応を取り消し、描画も止まる。移動開始で反応を止め、呼びかけで移動を解除する。古い輪郭を拒否し、モデル再読込と期限切れの呼びかけを再生しないことを確認。
- OSの動きを減らす設定では骨を動かさず、静的な表情と一度の復帰描画だけ。反応中の繰り返し描画がないことをフレーム数で確認した。
- 通常・頷き中・終了後の自分のキャンバスを画像で確認。頷き中は頭と目線がわずかに下がり、全身と透明な余白は維持されている。動作の自然さ・気づきやすさは静止画だけでは評価を完了しない。
- 新しい操作窓の配置は機能検査のみ。隠した検証窓からの画像取得はUnknownVizErrorとなり、最新の操作窓全体の目視は未完了。以前の画像を最新版として使わない。

型検査・単体テスト31件・Build、Electron検査23項目が成功。依存関係の追加なし、`npm audit`の既知の脆弱性0件。検査用設定は通常設定から分離し、通常設定が変わらないことと、終了後に記録したプロセスが残らないことを確認した。呼びかけ中の別アプリへの実入力、物理トレイ操作、長時間負荷の再測定は未検証。ドラッグ後の焦点問題も継続する。

## 大きさの調整

小240×352、標準300×440、大360×528の3段階を追加。操作窓とトレイの「大きさ」で選ぶ。通常は下辺中央を保ち、画面端では全身が作業領域内に収まるよう補正する。選択は保存され、「画面端に戻す」や再起動でも保つ。

- 実マウスで操作窓の「小」を選び、(1500,580,300,440)→(1530,668,240,352)を確認。下辺中央を維持した。
- その後の実マウス入力は利用者の入力と重なり、操作窓も最小化されたため、前面化を繰り返さず終了した。「大」「標準」の実マウス選択を成功扱いにはしない。
- 3サイズすべてでElectronの実ウィンドウ寸法、描画寸法、輪郭の範囲、サイズ変更後の復帰位置を検査。各キャンバスの画像を目視し、頭・髪・足が切れていないことを確認した。これはデスクトップ全体のスクリーンショットではない。
- 非表示中の変更では窓を出さず描画もしない。表示すると新しい寸法で再開する。移動中の変更は古い輪郭を先に解除し、古い入力を拒否する。
- サイズのない旧設定は標準として読み込み、保存された任意の幅・高さは採用しない。不正値と極端に狭い作業領域も単体テストで確認。元のウィンドウサイズを大きくして入力範囲制限を迂回する画面側APIも拒否する。
- 設定・起動時データを`work/smoke-*`へ分けた検査環境で保存・再起動を確認し、通常の`local.config.json`が検査前後で同一であることを確認した。

型検査・単体テスト27件・Build、Electron検査19項目、`npm audit`の既知の脆弱性0件を確認。描画サイズの数値比較で検証スクリプトが一度タイムアウトしたが、整数寸法を使う検査に直して3サイズの画像取得まで再実施。残った検証アプリは終了ショートカットで正常終了し、以後の確認用アプリも終了済み。CPU/GPU/メモリのサイズ別比較はまだ行っていない。

入力焦点の追加調査では、Electronの`before-mouse-event`で画面への配送を止めても、Chromium側ではその呼出し後に焦点・マウス捕捉処理へ進むことを確認。これだけで焦点を保てるとは言えないため採用しなかった。直接移動後の焦点問題は未解決のまま。[Electronのパッチ](https://github.com/electron/electron/blob/v44.3.0/patches/chromium/revert_partial_remove_unused_prehandlemouseevent.patch#L39)、[Chromiumの入力処理](https://github.com/chromium/chromium/blob/152.0.7977.78/content/browser/renderer_host/render_widget_host_view_event_handler.cc#L349)

## 直接つかむ操作の追加

通常時は本体を含めて全面クリック通過のまま。`Ctrl + Alt + Shift + M`、トレイ、操作窓のボタンで一度だけ移動を開始する。現在の姿勢を固定し、自分のWebGLキャンバスのalphaを1回だけ読み、可視画素だけをWindowsの入力範囲にする。手を離す・取消・非表示・画面端復帰・描画停止・30秒の無操作で解除する。繰り返しの画面取得、マウス監視、追加の依存関係やAPIはない。

| 今回の項目 | 結果 |
| --- | --- |
| 実ショートカット | 別プロセスの入力欄を選んだ状態からMで移動を有効化。開始時点では入力欄と焦点を維持 |
| 本体の実ドラッグ | Windowsの実マウスで(900,300)→(926,341)、続いて(926,341)→(909,311)。つかんだ位置との差分どおりに移動し、手を離すと移動モードが解除 |
| 移動中の余白 | 透明余白に重なった別プロセスのボタンを実クリックし、0→1。移動モードは継続 |
| 通常時の本体 | 移動解除後、不透明な胴体の画素上を実クリックし、背後のボタンが1→2 |
| 輪郭と負荷の範囲 | 同モデルでは264矩形の例。固定した描画画素と入力範囲の差分0をElectron検査で確認。移動待ち中は繰り返し描画が停止。CPU/GPU/メモリの新版比較測定は未実施 |
| **ドラッグ後の入力焦点** | **未解決。** 実ドラッグ直前に別プロセスのfocused=true、直後はfalseを2回観測。しずく自身はfocused=false。別窓の入力欄選択は残るが、すぐ文字入力できるとは言えない。手操作での再現確認を依頼済み |

焦点の切り分けでは、Computer Useの前面化だけ、および同じ移動をIPCから直接呼ぶ検査では、別プロセスの焦点が維持された。実マウスの処理経路で差が出るが、原因は確定していない。`focusable:false`を維持し、他アプリの焦点を強制的に戻す処理は追加していない。移動後に入力が戻らなければ、作業中の入力欄をクリックし直す必要がある。

また、このPCではElectronの既定の`floating`レベルだと`isAlwaysOnTop=false`となり、別アプリの背後へ回る問題を確認。`pop-up-menu`レベルの明示指定でtrueとなり、別アプリを前面にしても描画を確認できた。Electronの該当版には既定レベルをタスクバーの背後へ置き直す処理があり、実測と整合するが、タスクバーの実状態は調査していない。[Electron 44.3.0実装](https://raw.githubusercontent.com/electron/electron/v44.3.0/shell/browser/native_window_views.cc)、[Windowsの配置仕様](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowpos)。作業領域内への制限は維持。自動非表示タスクバー、ポップアップメニュー、全画面アプリとの表示順は未検証。

形状指定にはWindows対応の実験的API `setShape` を使用。空配列は窓全体へ戻るため、必ずクリック通過を先に有効にする。矩形の数・座標・範囲・送信元を検査し、不正な輪郭は移動を取消。古い移動セッションの入力が次の移動を変更しないことも検査する。[Electronの形状仕様](https://www.electronjs.org/docs/latest/api/base-window#winsetshaperects-windows-linux-experimental)

なお、CSSの標準ドラッグ領域は今回の非フォーカス窓で動かなかったため採用していない。押下・移動・解放イベントで自分の窓だけを動かし、開始時のつかんだ位置を保持する。生の実機記録はGit管理外の `work/native-move-check.json`。

## 負荷計測

以下は直接移動を追加する前の版（369344aまで）の測定値。新版の負荷改善を示す数値ではない。このPC上の短時間の開発ビルド検証であり、長時間の安定性やほかのPCの軽さを保証しない。ElectronをPlaywrightで起動して測定し、計測操作自体の影響も含む。他アプリを停止して専有した環境ではない。

- Windows 11 Home 10.0.26200、16論理CPU、約15.8GiB RAM。
- Intel UHD Graphics / NVIDIA GeForce GTX 1650。GPU計測は当該アプリのPIDに帰属するエンジンのみ。
- 主画面1920×1080、作業領域1920×1032、倍率100%。別画面も125%で接続されていた。動作対象は主画面だけ。
- AvatarSample_A、18,495,760 bytes、46,984 triangles、20 draw calls。VRM 1.0。
- 表示300×440、DPR1、30fps上限、影なし。実測FPSは上限より低く、30fps固定達成を主張しない。
- CPUは同一プロセスの累積CPU秒の差分を、区間の経過秒と16論理CPUで割ったPC全体比。時間で重み付けして平均する。メモリは対象プロセスのWorking Setの合計（共有ページの重複を含み得る）とPrivate Bytesの合計（割り当て済み専用メモリで、常にRAMへ載っている量ではない）。
- 表示・非表示を別の期間として集計し、それぞれ最初の10秒を除外。モデル読込済み、同じ4プロセスのPIDと起動時刻、単調に増える時刻、測定範囲を検証した。古いログ、不正値、区間内の表示状態変更は成功として扱わない。
- GPUはWindows `GPU Engine/Utilization Percentage` を2秒間隔で取得。同一物理エンジンについて対象PIDを合算し、最大値を代表値にする。PC全体のGPU使用率とは異なる。

| --- | --- | --- |
| CPU平均（PC全体比） | 1.206% | 0.0265% |
| Working Set合計・平均／最大 | 493.80／531.72MiB | 480.28／481.67MiB |
| Private Bytes合計・平均／最大 | 481.73／520.98MiB | 465.80／468.94MiB |
| CPU・メモリの有効測定時間 | 134.55秒、68時点 | 210.85秒、106時点 |
| GPU平均／最大 | 2.290／3.617% | 0.000／0.000% |
| GPUの有効測定 | 118.48秒、59サンプル | 59.13秒、30サンプル |
| 描画 | 区間末尾25.9fps、途中26.4fps | 約221秒、3,738フレームから増加なし |

GPU取得中にWindowsカウンターの無効値が発生したため、無効値を0にせず除外して非表示区間を再測定した。GPUはCPU・メモリより短い部分区間の測定。以前の「CPU0.41%、メモリ582.2MiB」は表示・非表示・操作窓を混ぜた途中の補足値で、上表とは条件が異なるため置き換えた。

17:13ごろの物理Escapeによる中断後、利用者の再開依頼を受けて続行。18:05に前回からのアプリを正常終了し、保存待ちだった時系列データを確定・集計した。起動から約58分生存していたが、その大半は非表示であり、連続表示の長時間耐久試験とはしない。再開後の更新検査も終了済み。

生データはGit管理外の `work/gpu-visible-final.json`、`work/gpu-hidden-final.json`、`work/measurement-periods.json`、`work/metrics.json` に保持。集計結果は `work/performance-summary.json`。`node scripts/summarize-metrics.mjs` で再集計できる。同じ計測PCでの実行を前提に論理CPU数を取得し、別のPCで集計する場合は環境変数 `SHIZUKU_CPU_COUNT` に計測元の論理CPU数を指定する。

Electronの取得ZIPは158,149,320 bytes（約150.8MiB）、展開した実行本体367.4MiB、開発用依存全体471.8MiB、アプリの生成コード0.75MiB。キャッシュ・VRM・実行データは別。インストーラーの配布容量ではない。

## 残る確認

- **タイトルバーの実ドラッグは未検証。** 再開後、別アプリのウィンドウが重なり、Computer Useの対象一致チェックでドラッグが拒否された。前面化後も対象外の画面が見えたため、その座標への操作を続けていない。矢印ボタンと移動イベントの追従を、実ドラッグ成功へ読み替えない。利用者の手元での確認を依頼済み。
- 直接移動の追加後、操作窓の実画面を見て開始ボタンからの有効化も確認。タイトルバーへのドラッグ入力は再送できたが窓の座標は変わらず、こちらの手操作相当の成功確認には至っていない。記録は `work/control-title-drag-check.json`。
- 実マウスでの通知領域アイコン選択とメニュー全項目の通し操作は未検証。実際のElectronメニューの処理は検査済み。終了用ショートカットは実操作した。
- ダブルクリック、ショートカット競合、壊れたモデル全般、スリープ復帰、長時間、バッテリー、高負荷時、別GPU・別VRM、インストーラー配布は未検証。
- 実機に画面が2枚あるため、物理的に1枚だけ接続した環境を検証したとは言わない。複数画面対応も完成していない。
- 通常時はキャラクター全体がクリック透過。直接移動は明示開始で一度だけ使う。呼びかけ・会話はまだない。
- 新アプリはlocal Gitのみ。新GitHubの公開範囲・アプリ全体のソースライセンスは未決定。

## 判断と次の区切り

透明表示・復帰と、直接つかむ移動の試作は成立したが、ドラッグ後の入力焦点に未解決の検証結果がある。まずこの確認、トレイ・常駐の手触りと負荷の許容判断を進める。次の順番は [ロードマップ](roadmap.md) に記録。今はAPI料金も常時監視もない。

Notion全体ロードマップへ反映する案：「透明常駐・復帰に加え、明示開始の直接移動を試作。実ドラッグ・余白通過は確認。ドラッグ後の入力焦点に課題、トレイ通し操作・長時間評価は残る」とする。「会話・音声接続」「独自VRM」「配布」「複数画面」は未着手のまま。今回Notion自体は更新していない。
